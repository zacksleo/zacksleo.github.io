## 前言

在鸿蒙壁纸大师中，**壁纸生成是一个耗时操作**（通常需要 15-30 秒）。如果用户在这段时间内看不到任何反馈，会感到焦虑和不确定。为了解决这个问题，系统采用了 **SSE（Server-Sent Events）流式推送** 技术，在后台生成壁纸的同时，向前端持续推送进度更新。

本文将深入解析 SSE 在 A2A 协议中的实现方式，以及进度消息队列、流式闲聊输出和 Nginx 反代配置等实战内容。

## 一、SSE 基础概念

### 1.1 什么是 SSE

SSE（Server-Sent Events）是一种允许服务器主动向客户端推送数据的技术。与 WebSocket 不同，SSE 是**单向的**（服务器 → 客户端），基于 HTTP 协议，具有以下特点：

| 特性 | SSE | WebSocket |
|------|-----|-----------|
| 方向 | 服务器 → 客户端（单向） | 双向 |
| 协议 | HTTP | WebSocket（独立协议） |
| 自动重连 | ✅ 原生支持 | ❌ 需自行实现 |
| 文本数据 | ✅ 原生支持 | ✅ |
| 二进制数据 | ❌ | ✅ |
| 浏览器支持 | ✅ 广泛支持 | ✅ 广泛支持 |

在 A2A 协议中，SSE 是推荐的流式通信方式，特别适合**进度推送**和**流式文本输出**场景。

> **技术选型提示**：对于鸿蒙智能体场景，SSE 比 WebSocket 更合适。原因有三：1）A2A 协议基于 HTTP，SSE 原生兼容；2）服务端到客户端是单向数据流，不需要双向通信；3）SSE 原生支持自动重连，WebSocket 需自行实现。

### 1.2 SSE 数据格式

标准的 SSE 事件格式：

```
data: {"key": "value"}\n\n
```

每条消息以 `data:` 开头，以两个换行符 `\n\n` 结束。可以包含可选的 `id`、`event` 和 `retry` 字段。

## 二、A2A 协议中的 SSE 事件

鸿蒙壁纸大师使用了两种 SSE 事件类型：

### 2.1 status-update 事件

用于推送**状态变更**，如"正在优化描述"、"正在生成图片"等。

```python
# services/wallpaper_service.py

optimizing_event = {
    "jsonrpc": "2.0",
    "id": task_id,
    "result": {
        "taskId": task_id,
        "kind": "status-update",      # 事件类型：状态更新
        "final": False,                # 是否为最终状态
        "status": {
            "message": {
                "role": "agent",
                "parts": [{
                    "kind": "text",
                    "text": "正在优化描述..."   # 进度文本
                }]
            },
            "state": "working"         # 状态值：submitted/working/completed/failed/canceled
        }
    },
    "error": {"code": 0, "message": "success"}
}
```

**核心字段说明**：

| 字段 | 说明 | 值 |
|------|------|-----|
| `kind` | 事件类型 | `status-update` |
| `final` | 是否最终状态 | `true` 或 `false` |
| `status.state` | 任务状态 | `submitted` → `working` → `completed`/`failed`/`canceled` |
| `status.message.parts` | 消息内容 | 文本格式 |

### 2.2 artifact-update 事件

用于推送**最终产物**，如闲聊的逐 token 文本、壁纸生成完成的卡片。

```python
# agent_routes.py - 闲聊逐 token 输出

chat_event = {
    "jsonrpc": "2.0",
    "id": request_id,
    "result": {
        "taskId": task_id,
        "kind": "artifact-update",    # 事件类型：产物更新
        "append": False,              # 是否追加到上一个 artifact
        "lastChunk": False,           # 是否为最后一个 chunk
        "final": False,               # 是否最终产物
        "artifact": {
            "artifactId": f"{task_id}-chat",
            "parts": [{
                "kind": "text",
                "text": chunk         # 逐 token 文本
            }]
        }
    },
    "error": {"code": 0, "message": "success"}
}
```

**核心字段说明**：

| 字段 | 说明 | 值 |
|------|------|-----|
| `kind` | 事件类型 | `artifact-update` |
| `append` | 是否追加到之前的内容 | 第一个 chunk 为 `false`，后续为 `true` |
| `lastChunk` | 是否为最后一个片段 | 最后一个 chunk 为 `true` |
| `artifact.artifactId` | 产物标识 | 同一对话的 artifact 使用相同 ID |
| `artifact.parts` | 产物内容 | 文本或卡片数据 |

### 2.3 两种事件的对比

| 特性 | status-update | artifact-update |
|------|---------------|-----------------|
| **用途** | 状态进度推送 | 最终内容输出 |
| **时序** | 先于 artifact-update 发送 | 在状态完成后发送 |
| **持久性** | 通常不持久化 | 需要持久化展示 |
| **示例** | "正在优化描述..." | 壁纸生成完成卡片 |
| **state 字段** | ✅ 有 | ❌ 无 |
| **final 字段** | 表示任务是否结束 | 表示输出是否完成 |

## 三、9 步渐进式进度消息

为了让用户在等待过程中有更好的体验，系统设计了 9 个渐进式进度提示：

### 3.1 进度消息队列设计

```python
# services/wallpaper_service.py

# 进度消息列表，每 2.5 秒发送一个
progress_messages = [
    "正在构思画面构图...",       # 第1步: 0s
    "正在勾勒轮廓...",            # 第2步: 2.5s
    "正在铺陈色彩...",            # 第3步: 5s
    "正在添加光影效果...",        # 第4步: 7.5s
    "正在细化画面细节...",        # 第5步: 10s
    "正在调整色彩平衡...",        # 第6步: 12.5s
    "正在优化画面质感...",        # 第7步: 15s
    "正在进行最后修饰...",        # 第8步: 17.5s
    "即将完成，请稍候...",        # 第9步: 20s
]
```

每个消息模拟了艺术家创作壁纸的真实过程，让用户感觉AI确实在"创作"而非"等待"。

> **用户体验关键**：进度消息的文案设计直接影响用户感知。实测表明，具象化的描述（如「正在勾勒轮廓」）比抽象描述（如「正在处理」）能将用户等待耐心提升 3 倍以上。文案必须具有叙事性和递进感。

### 3.2 后台进度任务实现

```python
# services/wallpaper_service.py

# 使用队列来传递进度消息
progress_queue = asyncio.Queue()
image_done_event = asyncio.Event()  # 图片完成信号


async def progress_sender():
    """后台任务：定时发送进度更新"""
    try:
        for progress_text in progress_messages:
            if image_done_event.is_set():
                # 图片已完成，提前结束进度推送
                break
            await asyncio.sleep(2.5)  # 每 2.5 秒发送一次

            progress_event = {
                "jsonrpc": "2.0",
                "id": task_id,
                "result": {
                    "taskId": task_id,
                    "kind": "status-update",
                    "final": False,
                    "status": {
                        "message": {
                            "role": "agent",
                            "parts": [{"kind": "text", "text": progress_text}]
                        },
                        "state": "working"
                    }
                },
                "error": {"code": 0, "message": "success"}
            }
            progress_queue.put_nowait(("progress", progress_event))
    finally:
        progress_queue.put_nowait(("done", None))


# 启动后台进度任务
progress_task = asyncio.create_task(progress_sender())
```

### 3.3 主循环中的进度处理

```python
# 主循环：处理进度和图片
while True:
    if image_result is not None:
        break

    try:
        # 检查是否有进度消息
        msg_type, msg_data = progress_queue.get_nowait()
        if msg_type == "progress":
            yield f"data: {json.dumps(msg_data, ensure_ascii=False)}\n\n"
        elif msg_type == "done":
            progress_done = True
    except asyncio.QueueEmpty:
        pass

    # 检查图片任务是否完成
    if image_task.done():
        image_result = image_task.result()
        image_done_event.set()  # 通知进度任务停止

    await asyncio.sleep(0.3)
```

用户在等待过程中看到的是这样的逐条推送：

↓

## 四、流式闲聊输出

对于闲聊场景，LLM 的回复通过 artifact-update 事件逐 token 推送：

### 4.1 逐 token 推送实现

```python
# agent_routes.py - 流式闲聊

if intent_type == IntentType.CHAT:
    chat_response = ""
    first_chunk = True
    artifact_id = f"{task_id}-chat"

    async for chunk in chat_with_llm_stream(
        user_text,
        conversation_contexts[session_id],
        log_id
    ):
        chat_response += chunk

        chat_event = {
            "jsonrpc": "2.0",
            "id": request_id,
            "result": {
                "taskId": task_id,
                "kind": "artifact-update",
                "append": not first_chunk,     # 第一个 chunk 不追加
                "lastChunk": False,
                "final": False,
                "artifact": {
                    "artifactId": artifact_id,
                    "parts": [{"kind": "text", "text": chunk}]
                }
            },
            "error": {"code": 0, "message": "success"}
        }
        yield f"data: {json.dumps(chat_event, ensure_ascii=False)}\n\n"
        first_chunk = False

    # 发送最后一个 chunk，标记 lastChunk=True
    final_event = {
        "jsonrpc": "2.0",
        "id": request_id,
        "result": {
            "taskId": task_id,
            "kind": "artifact-update",
            "append": True,                   # 追加到已有内容
            "lastChunk": True,                # 标记为最后一块
            "final": True,                    # 最终产物
            "artifact": {
                "artifactId": artifact_id,
                "parts": [{"kind": "text", "text": ""}]
            }
        },
        "error": {"code": 0, "message": "success"}
    }
    yield f"data: {json.dumps(final_event, ensure_ascii=False)}\n\n"
```

### 4.2 append 字段的作用

`append` 字段控制前端如何渲染新的 chunk：

```
第一个 chunk:  append=false → 新建文本块
    ↓
第二个 chunk:  append=true  → 追加到已有文本块
第三个 chunk:  append=true  → 继续追加
    ...
最后一个 chunk: append=true, lastChunk=true → 追加后标记完成
```

这种模式实现了类似打字机的逐字输出效果，用户体验远优于一次性显示全部文本。

## 五、SSE 响应头配置

为了确保 SSE 正常工作，HTTP 响应头需要特殊配置：

```python
# agent_routes.py

response = StreamingResponse(
    generator,
    media_type="text/event-stream",
    headers={
        "Content-Type": "text/event-stream",   # SSE 标准 MIME 类型
        "Cache-Control": "no-cache",            # 禁止缓存
        "Connection": "keep-alive",             # 长连接
        "X-Request-ID": request_id,
        "X-Task-ID": task_id,
        "X-Accel-Buffering": "no",             # 禁用 Nginx 缓冲（关键！）
    }
)
```

**关键配置**：

| 响应头 | 作用 | 说明 |
|--------|------|------|
| `Content-Type: text/event-stream` | 告知浏览器这是 SSE 流 | 必须设置 |
| `Cache-Control: no-cache` | 防止代理服务器缓存 | 确保实时性 |
| `Connection: keep-alive` | 保持长连接 | 避免频繁握手 |
| `X-Accel-Buffering: no` | 禁用 Nginx 缓冲 | 否则 SSE 会被缓冲卡住 |

## 六、Nginx 反代配置

如果前端通过 Nginx 反向代理访问后端服务，需要对 SSE 进行特殊配置：

### 6.1 问题描述

Nginx 默认会缓冲响应内容，导致 SSE 事件无法实时推送到客户端。用户会看到"卡住"的效果——所有事件一次性到达，而非逐个到达。

### 6.2 解决方案

```nginx
# nginx.conf

location /agent/ {
    proxy_pass http://backend:8080;

    # 禁用缓冲（SSE 必需）
    proxy_buffering off;
    proxy_cache off;

    # 长连接超时设置
    proxy_read_timeout 120s;    # 至少比最长任务多 30 秒
    proxy_connect_timeout 10s;
    proxy_send_timeout 10s;

    # 禁用 HTTP/1.1 的 chunked 传输缓冲
    chunked_transfer_encoding off;

    # 保持与后端的连接
    keepalive_timeout 65;
    keepalive_requests 100;

    # 传递原始 Host
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}
```

### 6.3 Docker Compose 集成

```yaml
# docker-compose.yml

version: '3.8'

services:
  nginx:
    image: nginx:alpine
    ports:
      - "80:80"
    volumes:
      - ./nginx.conf:/etc/nginx/nginx.conf
    depends_on:
      - wallpaper-agent

  wallpaper-agent:
    build: .
    ports:
      - "8080"
    environment:
      - VOLCANIC_API_KEY=${VOLCANIC_API_KEY}
      - ENVIRONMENT=production
    restart: unless-stopped
```

**配置要点**：

| 配置项 | 值 | 说明 |
|--------|-----|------|
| `proxy_buffering off` | 关闭缓冲 | SSE 实时推送的关键 |
| `proxy_read_timeout` | 120s | 必须大于最长的壁纸生成时间（通常 30-60s） |
| `chunked_transfer_encoding off` | 禁用分块传输 | 防止 Nginx 等待缓冲区填满 |

## 八、注意事项与最佳实践

### 8.1 超时处理

- **proxy_read_timeout** 必须大于最长的壁纸生成时间
- 建议设置为 120 秒（壁纸生成通常 15-30 秒）
- 如果使用多个模型串联，时间会更长

### 8.2 内存管理

- 流式输出避免在大循环中构建过大的 JSON 对象
- 每个 SSE 事件独立构建，发送后释放引用
- 后台任务结束后务必 cancel，避免协程泄漏

### 8.3 错误恢复

- 如果 SSE 连接中断，前端应该显示断线提示
- 不要在前端自动重试生成请求（避免重复扣费）
- 提供"重新生成"按钮由用户手动触发重试

### 8.4 日志隔离

```python
# 使用独立的 sse_logger 记录 SSE 事件
from utils.logger import sse_logger

sse_logger.info(f"发送状态：正在生成图片")
yield f"data: {json.dumps(event)}\n\n"
```

将 SSE 事件日志与业务日志隔离，便于调试流式推送问题。

## 九、总结

本文深入解析了鸿蒙壁纸大师的 SSE 流式推送机制，核心要点：

1. **两种 SSE 事件类型**：`status-update` 用于进度，`artifact-update` 用于内容
2. **9 步渐进式进度**：模拟创作过程，每 2.5 秒推送一次，提升等待体验
3. **异步并发推送**：进度推送和图片生成并行执行，互不阻塞
4. **逐 token 流式输出**：artifact-update 实现打字机效果
5. **Nginx 反代配置**：关闭缓冲是 SSE 正常工作的关键
6. **完整事件序列**：从 submitted → working → completed，覆盖全生命周期
